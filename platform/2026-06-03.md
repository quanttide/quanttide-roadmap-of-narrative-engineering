# 写作云 Platform — Harness 工作蓝图

## 目标

构建一个轻量的 Agent Harness 层，位于应用代码和 LLM 之间，管理每一次 LLM 调用的生命周期、观测和容错。

## 当前状态

`call_llm()` 直接裸调 `LLM.complete()`，没有重试、没有日志、没有超时、没有 token 追踪。14 个集成测试依赖真实 DeepSeek API，但没有一个基础设施来管理这些调用的可靠性。

## 设计

```
应用代码 (main.py)
    │
    ▼
Harness 层
    ├── 重试策略      ← 502/429 自动重试 + 指数退避
    ├── 调用链日志    ← 每次 LLM 调用记录 prompt / response / 耗时 / token
    ├── 超时控制      ← 长文本分段或超时断开
    ├── token 预算    ← 防止单次调用消耗过多 token
    └── 失败快照      ← 异常时输出完整调用链（prompt + response + 错误）
    │
    ▼
LLM.complete() → DeepSeek
```

## 行动

### P0 — 核心 Harness

- [ ] `Harness` 类封装 `call_llm()`，提供重试 / 超时 / 日志能力
- [ ] `call_llm()` 改为调用 `Harness().complete()`
- [ ] 每次 LLM 调用自动记录到 `data/provider.log`（prompt 摘要 + response 前 200 字 + 耗时 + token）
- [ ] 502/429 自动重试（最多 3 次，指数退避：1s → 3s → 9s）
- [ ] 超时控制：单次 LLM 调用超过 60s 断开

### P1 — 可观测性

- [ ] 失败快照：异常时输出完整 prompt 和 response body 到日志
- [ ] 集成测试通过 `Harness` 的日志接口断言"发生了预期次数的 LLM 调用"
- [ ] 调用链追踪ID：每次请求（Flutter→Provider→LLM）生成唯一 trace_id，串联日志

### P2 — 测试 Harness

- [ ] 集成测试使用 `RecordingHarness`（Harness 子类），记录所有 LLM 调用但不实际执行，用于验证 prompt 构建正确
- [ ] 验收测试使用 `RetryingHarness`，允许 502 时自动重试
- [ ] 单元测试使用 `MockHarness`，替代当前的 `patch("app.main.call_llm")`

## 不做

- 不引入异步任务队列
- 不做 LLM 调用缓存（等需要时再考虑）
- 不做多模型路由（不需要切换模型）
- 不实现 /evaluate 端点（那是评估服务，不是 Harness）
- 不管理风格库

## 约束

- Harness 必须是纯同步的（FastAPI 同步路由调用）
- 不改动 Prompt 设计
- 不改动 API 响应模型
