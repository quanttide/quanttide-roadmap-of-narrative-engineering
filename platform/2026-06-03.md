# 写作云 Platform — 工作蓝图

## 当前状态

Provider API（alpha.5）已完成 StyleSample 驱动的 3R 重写。三个端点覆盖了从评审到深度分析到启发建议的全流程。14 个集成测试验证了核心业务逻辑。

## 下一阶段：评估基础设施

### 动机

今天集成测试中发现的五个 Harness 模式，本质上是 LLM 应用的评估方法论。当前这些模式只存在于测试代码中，没有产品化。下一阶段的工作是把这些约束变成可复用的评估服务，为写作质量和风格匹配提供可量化的基础。

### 核心概念：评估服务

```
POST /evaluate
{
  "text": "...",
  "references": [
    {"style": campus_style, "label": "校园言情"},
    {"style": urban_style, "label": "职场言情"}
  ]
}
→ {
  "results": [
    {"label": "校园言情", "alignment_score": 0.82},
    {"label": "职场言情", "alignment_score": 0.35}
  ],
  "conclusion": "文本更接近校园言情风格"
}
```

这本质上是今天 review 测试的产品化。它与 `/review` 的区别在于：

| | `/review` | `/evaluate` |
|------|-----------|-------------|
| 输入 | 文本 + 一个风格 | 文本 + 多个候选风格 |
| 输出 | 维度级分析 | 风格级排名 |
| 用途 | 写作辅助 | 风格分类、质检、归因 |

### 行动项

#### P0 — 评估服务

- [ ] `POST /evaluate` 端点：接受 text + 多个 style，返回每个 style 的对齐分数和排名
- [ ] 内置正样本/负样本校验：请求中可标注 expected_label，响应标示是否符合预期
- [ ] 相对比较保证：一次请求内评估所有候选风格，确保分数可比较（不是跨请求）

#### P1 — 评估基础设施完善

- [ ] LLM 调用层抽象：将今日手动实现的"存在性检查""失败快照""相对比较"模式编码为可复用的 Harness 类
- [ ] 重试与退避策略：502/429 时自动重试，指数退避
- [ ] 调用链日志：每次 LLM 调用自动记录 prompt、response、耗时、token 数，失败时输出快照
- [ ] 超时控制：长文本分段或超时断开

#### P2 — 风格管理

- [ ] `GET /styles`：列出可用风格
- [ ] `POST /styles`：注册新风格（上传 style.yaml + sample.md）
- [ ] 内置风格库：校园言情、职场言情、克制浪漫等预设风格

#### P3 — 写作质量面板

- [ ] 写作趋势：多轮评审的 alignment_score 历史曲线
- [ ] 风格迁移检测：同一文本对不同风格的分数变化，检测风格漂移
- [ ] 批量评估：一次评估多篇文本，输出质量报告

## 不做

- 不做用户系统（多租户、权限）
- 不做 OpenCode 对话集成
- 不重构 Flutter 前端（维持现状，前端策略单独规划）

## 当前项目结构

```
apps/qtcloud-write/src/provider/
├── app/
│   ├── main.py           ← 三个端点 + prompts
│   ├── models.py         ← Style / Sample / Dimension / 请求响应模型
│   ├── config.py         ← 配置 + 路径
│   └── services/
│       └── llm.py        ← call_llm + LLM 客户端
├── tests/                ← 6 单元测试（mock call_llm）
├── integrated_tests/     ← 14 集成测试（真实 DeepSeek API）
│   └── fixtures/         ← 测试数据（校园/职场言情样本）
└── data/                 ← SQLite + 日志
```
