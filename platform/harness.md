# Harness — LLM 评估判断框架

Harness 不是库，不是基础设施层，不是测试策略。Harness 是系统在做每一次评估时必须遵循的五条判断准则。

## 五条准则

### 1. 相对判断

系统必须支持在一次请求内比较多个候选，输出相对分数，而非绝对分数。

```
POST /evaluate
{"text": "...", "candidates": [style_A, style_B]}
→ 风格 A: 0.82, 风格 B: 0.35 （同一轮，可比）
而非 → 风格 A: 0.82               （跨请求，不可比）
```

理由：LLM 输出的绝对数值不可信，但同一轮内的排序可信。

### 2. 双向校验

任何"文本是否符合风格"的判断，必须同时包含正反两个方向。

```
❌ 只判断"文本是否符合风格 A"
✅ 同时判断"文本是否符合风格 A"和"是否符合风格 B"
   → 风格 A 分高，风格 B 分低，结论才有意义
```

理由：单方向判断无法排除"对所有文本都高分"的基线漂移。

### 3. 负样本感知

系统必须知道"我不知道"。当输入超出训练范围（如非文学文本），应给出明确信号而非模糊高分。

```
输入：天气预报 → 所有风格分数 ≤ 0.3
输入：校园言情 → 匹配风格 ≥ 0.6，不匹配风格 ≤ 0.4
```

理由：没有负样本控制的系统无法区分"匹配"和"无法判断"。

### 4. 存在性优先

当 LLM 输出不可控时，系统应以"存在/不存在"而非具体数值作为判断依据。

```
❌ 依赖 "alignment_score > 0.5" 做决策
✅ 依赖 "deviation 列表不为空" 做决策
```

理由：数值受 prompt 措辞、模型版本、温度参数影响。存在性是唯一稳定的信号。

### 5. 可追溯

每一次评估必须能回答"为什么是这个结论"。

```
POST /evaluate + trace_id: req_001
→ 日志:
  req_001 → 候选 A prompt: 3.2k tokens → 响应 0.82
  req_001 → 候选 B prompt: 3.2k tokens → 响应 0.35
  req_001 → 结论: 更接近风格 A（理由：xxx）
```

理由：LLM 的判断不是确定性的。没有追溯能力就无法 debug、无法改进、无法对用户负责。

## 产品形态

这五条准则不依赖特定的实现。它们可以表现为：

| 准则 | 产品形态 |
|------|---------|
| 相对判断 | 评估端点接受多个候选 |
| 双向校验 | 评估报告同时显示正反分数 |
| 负样本感知 | 置信度字段（低置信度时告知用户"不确定"） |
| 存在性优先 | 偏差列表而非分数仪表盘 |
| 可追溯 | 评估结论附带依据摘要 |

## 工作量预期

Harness 不是核心业务逻辑。在 LLM 驱动的系统中，**约 80% 的代码是 harness**——重试机制、JSON 验证、pairwise 对比框架、日志追溯、温度参数控制——这些非功能代码保护着 20% 的核心逻辑（prompt 构建、结果解析、评分聚合）。比例可能更高。这与微调和 prompt engineering 有相似的内在逻辑：约束一部分就必然损失一部分，设计上必须精炼，不能过于复杂。
